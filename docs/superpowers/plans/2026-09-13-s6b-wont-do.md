# S6b "Won't-do outcome" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A field user who cannot do a task — the plant room is locked, load shedding, the contractor did not come, no materials — records "Can't do" with a mandatory reason instead of leaving the task to go overdue or ticking it as done. The reason is stored on the completion row, the task carries a fifth status `wont_do`, every count in the system treats it the same way (neither done nor not-done; counted as activity for coverage; `missed` for PPM), the task list shows it with its reason, the evidence pack prints it, and admins and managers read yesterday's can't-dos in the digest.

**Architecture:** One migration, `2026-09-16_01_wont_do.sql`: `task_instances_status_check` restated with `wont_do`; `task_completions.outcome` (`completed|wont_do`, default `completed`) and `task_completions.reason`; `complete_task` re-created with two more parameters (`p_outcome`, `p_reason`) — the five-argument function is **dropped first**, because `create or replace` with a different parameter list makes a second overload and PostgREST then refuses the old five-name call as ambiguous; `snapshot_building_metrics` restated whole (plpgsql) with `wont_do` out of every task count; `portfolio_coverage.completed_yesterday` counts `wont_do` as activity; `ppm_monthly_status` maps `wont_do` to `missed`, with that arm placed **before** the `tc.id is not null` arm (a can't-do has a completion row and would otherwise read as done). The reason vocabulary lives once, in `supabase/functions/_shared/wontDo.ts` (pure, no imports, Deno-bundled into `daily-digest`), re-exported to the app as `src/lib/wontDo.ts`, and mirrored in the RPC's check. `CompleteTaskDialog` grows a Done / Can't do segmented control and a reason list; the offline payload gains optional `outcome` and `reason` (optional so ops queued before the deploy replay as plain completions); `handlers.ts` passes them to the RPC; replay idempotency is unchanged (keyed on the client completion id). `TasksList` renders the status, badge and reason; `ChecklistsTab` adds a fourth "Can't do" card and reads `outcome, reason` from the `task_completions` query it already makes. `buildingScore.ts` names the two unscored statuses explicitly; the digest's coverage section carries "N tasks couldn't be done yesterday" with up to five `<building> · <task> · <reason>` lines, fed by one service-role query in `daily-digest` (`portfolio_coverage()` is unchanged).

**Tech Stack:** Postgres 17 (plpgsql, `pg_cron`), Supabase JS + PostgREST, React 18 + TS, vitest + Testing Library, Node smoke scripts, Deno edge function (`daily-digest`).

**Spec:** `docs/superpowers/specs/2026-09-13-pilot-field-design.md` §5 (+ §2 constraints, §6 deploy). §5.3 is the table every status enumeration must answer to; the self-review at the bottom maps each row to a step.

/**
 * The "Can't do" reason vocabulary (S6b, spec §5.1). Pure and import-free: bundled into the
 * daily-digest edge function (its coverage lines print the label) and re-exported to the web app
 * through src/lib/wontDo.ts, so the list is written once. The complete_task RPC mirrors it
 * (2026-09-16_01_wont_do.sql, the check inside the function): change both together.
 *
 * Stored form (`task_completions.reason`): `<code>` for the four fixed codes, `other: <text>` for
 * free text — one column, human readable, filterable by prefix.
 */
export const WONT_DO_CODES = ['area_locked', 'load_shedding', 'contractor_absent', 'no_materials', 'other'] as const;
export type WontDoCode = (typeof WONT_DO_CODES)[number];

/** What a completion row says happened. Mirrors task_completions_outcome_check. */
export type TaskOutcome = 'completed' | 'wont_do';

export const WONT_DO_LABELS: Record<WontDoCode, string> = {
  area_locked: 'Area locked',
  load_shedding: 'Load shedding',
  contractor_absent: 'Contractor absent',
  no_materials: 'No materials',
  other: 'Other',
};

export const OTHER_PREFIX = 'other: ';

export function isWontDoCode(v: unknown): v is WontDoCode {
  return typeof v === 'string' && (WONT_DO_CODES as readonly string[]).includes(v);
}

/** The value to store; null when `other` carries no text (the dialog refuses to submit that). */
export function formatReason(code: WontDoCode, otherText = ''): string | null {
  if (code !== 'other') return code;
  const text = otherText.trim();
  return text ? `${OTHER_PREFIX}${text}` : null;
}

/** The stored value back into code + free text. Unknown input parses as `other` with the raw text; never throws. */
export function parseReason(reason: string | null | undefined): { code: WontDoCode | null; text: string } {
  const r = (reason ?? '').trim();
  if (!r) return { code: null, text: '' };
  if (r === 'other') return { code: 'other', text: '' };
  if (isWontDoCode(r)) return { code: r, text: '' };
  if (r.startsWith(OTHER_PREFIX)) return { code: 'other', text: r.slice(OTHER_PREFIX.length).trim() };
  return { code: 'other', text: r };
}

/** Human text for a stored reason: the label, or the free text itself for `other`. Empty when there is none. */
export function reasonLabel(reason: string | null | undefined): string {
  const { code, text } = parseReason(reason);
  if (!code) return '';
  return code === 'other' ? text || WONT_DO_LABELS.other : WONT_DO_LABELS[code];
}

/**
 * Per-building operational score: task completion over a rolling window.
 * completed ÷ (completed + pending + overdue) × 100, rounded; null when there are
 * no tasks (honest empty-state, never NaN). Display-only; the building's tasks live
 * in task_instances. Paired with the real OHS compliance % (compliance_scores).
 *
 * Two statuses are outside the score on purpose, and are named here rather than dropped by
 * omission: `issue_logged` (the answer was a problem, not a completion — it was never counted,
 * and nothing changes for it) and, since S6b, `wont_do` (closed with a reason: neither done nor
 * outstanding). The nightly snapshot (snapshot_building_metrics) draws the same line, so the
 * snapshot path and this live fallback agree.
 */
export interface TaskCounts {
  completed: number;
  pending: number;
  overdue: number;
}

export const UNSCORED_STATUSES: readonly string[] = ['issue_logged', 'wont_do'];

/** Bucket raw `task_instances.status` values into the three that score; everything else is ignored. */
export function countForScore(statuses: readonly (string | null | undefined)[]): TaskCounts {
  const c: TaskCounts = { completed: 0, pending: 0, overdue: 0 };
  for (const s of statuses) {
    if (s === 'completed') c.completed++;
    else if (s === 'pending') c.pending++;
    else if (s === 'overdue') c.overdue++;
    // UNSCORED_STATUSES (and any value the check constraint does not know) fall through.
  }
  return c;
}

export function taskCompletionPct(c: TaskCounts): number | null {
  const total = c.completed + c.pending + c.overdue;
  return total > 0 ? Math.round((c.completed / total) * 100) : null;
}

Ambiguities resolved (say so in the report if the controller wants them otherwise):

1. **Drop, don't replace.** The spec says "replace the function with the wider signature". `create or replace function` with a different parameter list does not replace in Postgres; it adds an overload, and PostgREST then answers the shipped five-name call with `PGRST203 Could not choose the best candidate function`. The migration drops `complete_task(uuid,uuid,text,boolean,jsonb)` first; the verify script asserts one `pg_proc` row and calls the old shape by name.
2. **The vocabulary module lives in `supabase/functions/_shared/`** and `src/lib/wontDo.ts` re-exports it. The digest prints reason labels and cannot import from `src/`; duplicating the five codes in three places (SQL, app, digest) is the alternative. The SQL mirror is unavoidable (the RPC must refuse bad input without a round trip) and is commented on both sides.
3. **Reason "select" is a radio list**, five rows of 44 px. On a phone it is one tap, not open-scroll-tap; in jsdom it is a click, where Radix `Select` needs the pointer-capture polyfill. Same labels, same codes.
4. **`ppm_monthly_status` arm order.** The spec says "maps to `missed`"; taken literally as another `when` after `tc.id is not null` it would read every can't-do as `done`, because a can't-do HAS a completion row. The `wont_do` arm comes first and tests both the instance status and the completion's `outcome`.
5. **Snapshot "by the day".** A can't-do is excluded from a day's counts only once it was recorded by that day (SAST `completed_at`, the same test `done` uses), so a reconstructed earlier day still sees it as open. Today's row is what the spec asks; earlier days stay honest.
6. **`ChecklistsTab` progress denominator** excludes can't-dos too ("1 / 3 tasks", 33 %), matching `buildingScore` and the snapshot. The spec names only the fourth list for this tab; leaving the tab's own percentage counting can't-dos as not-done while the header score does not would show two numbers for one building.
7. **The CSV export gains a "Reason" column.** Not in the spec; the export already prints status and completion columns, and a `wont_do` status with no reason beside it is half a record.
8. **Payload fields are optional**, not required as the spec's wording might suggest, so an op persisted in IndexedDB before the deploy still satisfies the type and replays as a plain completion. The dialog always sets both.
9. **`useDashboardStats` untouched** by evidence, not assumption: three positive-list queries, each cited by line.
10. **The evidence pack menu stays on can't-do rows.** `TasksList` offers it on any row with a completion; a can't-do has one and a signed record of "why not" is precisely what gets asked for.
11. **Digest count line + capped lines, heading unchanged.** "One line … with up to five lines" is read as: the section's first can't-do line carries the count, then at most five detail lines and "…and N more"; the `Coverage:` heading keeps its existing two counts so the eight existing coverage tests hold.
12. **iOS is flagged, not fixed.** The 2026-08-04 header says iOS hard-decodes `task_instances.status`. This plan cannot verify the Swift side; the apply checklist makes it an owner item before the first prod can't-do.
13. **S6a's refetch block in `CompleteTaskDialog` is carried, not overwritten.** At planning time the tree held an uncommitted S6a change to the dialog (query invalidation after a synced completion, three tests). Spec §3 says S6a does not touch the dialog; it does now. Task 3's rewrite includes the block and its tests stay; the two slices' dialog work lands as two commits on the same file, S6a first.

- Is there an iOS build that tolerates or knows `wont_do`? If not, the prod apply is safe (no row has the status until someone records one) but the Vercel promotion is the moment of exposure.
- Should a can't-do on a task with `requires_photo` still *offer* the photo (as planned, optional) or hide it entirely? The spec says "photo optional"; planned as offered-optional.
